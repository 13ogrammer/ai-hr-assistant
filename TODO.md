Concrete, specific gaps identified during manual testing but not fixed - not the chapter-level roadmap, which is in [PLAN.md](PLAN.md).

- **Pure embedding search misses short acronyms.** "how much lsl am i entitled to?" fails to retrieve the actual long service leave entitlement chunk (it surfaces the casual-employee entitlement, redundancy payout, and leave loading chunks instead) - the same question spelling out "long service leave" retrieves the right chunk at rank 1. The model correctly refuses ("I don't know") rather than guessing from weak context, which is the right behavior given what it's shown, but the retrieval gap itself is real. This is Chapter 9's problem (hybrid keyword + vector search), now with concrete evidence instead of a hypothetical.
- **The model does unflagged arithmetic on retrieved numbers.** Asked to convert "8.67 weeks" to hours, it correctly found a separately-retrieved chunk stating "38 hours per week" and multiplied them (329.46 hours) - genuinely grounded, not hallucinated, and correct this time. But the answer presents a model-computed number with the same confidence as a directly-quoted policy figure, and nothing in the system would catch it if the arithmetic were wrong. Relevant to Chapter 5's "compute comparisons in code, don't trust the model with numbers" principle.
- **A single paragraph larger than the chunk size cap is kept whole, never split further.** `chunk_text` in `apps/api/ingestion/ingest.py` has no hard ceiling - no evidence yet this is hurting real retrieval quality, so left as-is until it demonstrably does.
- **Access control only has role tiers, not per-document ownership.** Chapter 2's `allowed_roles` filter answers "can any role-X person see this chunk," not "can this specific person see this chunk." That's fine for company-wide policy and for the CEO's contract (no fake user is the CEO, so it degenerates cleanly to role-gating), but it can't express a realistic rule like "an employee's own contract is visible to them and HR, but no other employee or manager" - that needs an identity comparison, not a role tag, on a document that's fundamentally shared/role-scoped otherwise. Revisit if a later chapter's scenario needs "my own record" document access (most likely when Chapter 3's tool-based identity lookups meet document retrieval) - possibly an `owner_employee_id` column OR'd into the retrieval filter alongside `allowed_roles`, rather than restructuring the chapter split.
