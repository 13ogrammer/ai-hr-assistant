Concrete, specific gaps identified during manual testing but not fixed - not the chapter-level roadmap, which is in [PLAN.md](PLAN.md).

- **Pure embedding search misses short acronyms.** "how much lsl am i entitled to?" fails to retrieve the actual long service leave entitlement chunk (it surfaces the casual-employee entitlement, redundancy payout, and leave loading chunks instead) - the same question spelling out "long service leave" retrieves the right chunk at rank 1. The model correctly refuses ("I don't know") rather than guessing from weak context, which is the right behavior given what it's shown, but the retrieval gap itself is real. This is Chapter 9's problem (hybrid keyword + vector search), now with concrete evidence instead of a hypothetical.
- **The model does unflagged arithmetic on retrieved numbers - still true for document-retrieved figures, structurally fixed for tool-returned ones.** Asked to convert "8.67 weeks" to hours, it correctly found a separately-retrieved chunk stating "38 hours per week" and multiplied them (329.46 hours) - genuinely grounded, not hallucinated, but presented with the same confidence as a directly-quoted policy figure, and nothing would catch it if the arithmetic were wrong. That's still true for numbers that come from `search_policies` chunk text. For numbers that come from `get_salary`/`get_leave_balance`, Chapter 5's tokenization closed this as a side effect: the model never sees the raw number (only an opaque token like `LEAVE_BALANCE_1`), so asking it to e.g. "convert my leave balance to hours" now reliably gets a plain refusal to calculate (with the real day figure still stated, never withheld) instead of a silently-computed answer - verified live across repeated runs, zero hallucinated conversions. Document-retrieved numbers remain ungoverned until free-text values are tokenized too (see the new entry below).
- **Free-text document content still carries real PII that reaches the model verbatim.** Chapter 5 tokenized structured tool results (employee identity, salary, leave balance) and the system-prompt roster, but deliberately left retrieved document chunks untouched - e.g. `11_CEO_EMPLOYMENT_CONTRACT_RESTRICTED.md`'s remuneration clause contains "a base salary of $420,000 per annum" as plain prose, sent verbatim whenever HR/Board retrieves that chunk via `search_policies`. This is a genuinely different problem from the structured case: there's no known field to swap, it needs PII detection over arbitrary text (Presidio-style NER), not a lookup-table substitution. Deferred, not forgotten.
- **A single paragraph larger than the chunk size cap is kept whole, never split further.** `chunk_text` in `apps/api/ingestion/ingest.py` has no hard ceiling - no evidence yet this is hurting real retrieval quality, so left as-is until it demonstrably does.
- **HR's "list everyone" questions get silently wrong or refused answers.** `get_salary`/`get_leave_balance` only take a single `employee_id` - there's no bulk/aggregate tool. Asking as HR "how much leave does each of the employees have?" is non-deterministic across runs: once the model called `get_leave_balance` exactly once, for the caller's own id (treating "each of the employees" as "me"), and answered as if that satisfied the question - no error, no `BLOCKED`, just silently wrong scope. Another run made zero tool calls and answered "I don't know." Chapter 3's brief was single-identity lookups (an employee's own record, or HR targeting *any one* id) - never "list everyone" - so this is a real gap, not a regression. Fix is probably a dedicated bulk tool (e.g. `list_leave_balances()`, HR-only) rather than relying on the model to fan out into N parallel single-employee calls on its own.
- **Access control only has role tiers, not per-document ownership.** Chapter 2's `allowed_roles` filter answers "can any role-X person see this chunk," not "can this specific person see this chunk." That's fine for company-wide policy and for the CEO's contract (no fake user is the CEO, so it degenerates cleanly to role-gating), but it can't express a realistic rule like "an employee's own contract is visible to them and HR, but no other employee or manager" - that needs an identity comparison, not a role tag, on a document that's fundamentally shared/role-scoped otherwise. Revisit if a later chapter's scenario needs "my own record" document access (most likely when Chapter 3's tool-based identity lookups meet document retrieval) - possibly an `owner_employee_id` column OR'd into the retrieval filter alongside `allowed_roles`, rather than restructuring the chapter split.
